# ha-host-agent

Monitoring of Linux hosts (backup servers first) in Home Assistant:

- **agent** (`agent/`): Python agent on each host, publishing over MQTT the SMART health
  of the disks, filesystem usage, dirvish backups, job freshness (rsync, scripts...) and
  system health;
- **blueprint** (`blueprints/`): alert automation for any problem reported by the agents;
- **integration** (`custom_components/host_agent/`): adds a host from its IP and SSH
  credentials, installs, configures and updates the agent (with automatic rollback);
- **card** (`card/`): dedicated Lovelace card, served by the integration (nothing to
  declare in the dashboard resources).

## Integration

### Installation

HACS → **Integrations** → search *Host Agent* (until it is in the default list: ⋮ → *Custom
repositories* → `https://github.com/Elwinmage/ha-host-agent`, type *Integration*), install,
restart Home Assistant, then **Settings → Devices & services → Add integration → Host Agent**.
MQTT must be set up.

HACS installs the release archive `host_agent.zip`, which already contains the agent
(`custom_components/host_agent/agent/host-agent.pyz`): nothing to build.

### Adding a host

1. **SSH access**: host, port, an account allowed to use `sudo` (or root), with a password
   or an unencrypted OpenSSH private key. These credentials are used once and never stored.
2. **Host identity**: the SSH host key fingerprint is shown; once confirmed it is pinned and
   any later change is refused (repair issue + re-authentication).
3. **Agent settings**: device name, MQTT broker *as seen from the host*, MQTT account
   (preferably dedicated), language, automatic updates.
4. Installation (≈ 1 min): the integration prepares the host, installs the agent and waits
   for it to report over MQTT.

An existing manual installation is taken over: its `language` and `collectors` settings are
imported, the MQTT section is rewritten.

### What is created on the host

| Item | Purpose |
|---|---|
| `host-agent` system account | runs the agent (no shell, no home) |
| `host-agent-admin` account | used by Home Assistant; key only (password locked), `restrict`ed key |
| `/usr/local/lib/host-agent/host-agent-admin` | the **only** command `host-agent-admin` may run with sudo; validates every argument, checks the archive sha256, version and configuration before use, refuses links |
| `/etc/sudoers.d/host-agent-admin` | the rule above |
| `/etc/systemd/system/host-agent.service` | hardened unit (capabilities, `ProtectSystem=strict`) |
| `/opt/host-agent/versions/*`, `current` | installed versions (3 kept), active one |
| `/etc/host-agent/config.yaml`, `mqtt.secret` | generated by Home Assistant, `root:host-agent 0640` |

Home Assistant stores the host key and its own ed25519 key; a compromised Home Assistant can
install/restart/remove the agent on the host but has no shell and no write access to the backups.

### Agent updates

The agent version is bundled with the integration: updating the integration makes an
**Agent** update entity appear on each host device (or installs it automatically when the
option is enabled). An update:

1. uploads the archive and the configuration to the restricted account;
2. the helper checks sha256, version and configuration, switches `current`, restarts and
   checks the service stays up — otherwise it restores the previous version and configuration;
3. Home Assistant then waits for the new version to report over MQTT (2 min) and rolls back
   if it does not.

### Options

**Settings → Devices & services → Host Agent → Configure** opens a menu:

| Menu | Settings |
|---|---|
| General | language, automatic agent updates |
| Disks | SMART reading interval, temperature thresholds, self-test schedule (short / long / time window), ignored disks |
| Filesystems | mountpoints that must be mounted, mountpoints to watch, used space thresholds |
| dirvish backups | banks (default: `master.conf`), ignored vaults, maximum age, timeline length, rsync 24 handling |
| Jobs | add / edit / delete jobs: newest file matching a glob (+ optional success regex), or a report pushed with `host-agent report` |
| System | CPU temperature and memory thresholds, Raspberry Pi power, clock synchronisation |
| RAID and ZFS | pool capacity thresholds, maximum scrub age |
| Graphics cards | temperature and video memory thresholds, slowdown alerts |
| systemd services | services that must run, failed units to ignore |
| Package updates | check interval, security updates as a warning |
| Kernel log | window, extra patterns, messages to ignore |
| Advanced | the whole `collectors` section in YAML ([`config.example.yaml`](agent/packaging/config.example.yaml) syntax) |

Every change is sent to the host and validated by the agent itself before being saved; a
refused configuration is never applied and the form shows the agent's message.

## Card

Served by the integration and loaded automatically: add a card, pick **Host Agent** and
the host. YAML:

```yaml
type: custom:host-agent-card
device_id: 0123abcd...      # the host device (visual editor)
# node_id: bkup             # instead of device_id, for an agent installed by hand
title: Serveur de sauvegarde  # default: device name
days: 14                    # backup timeline length
show: [issues, system, disks, filesystems, storage, gpus, vaults, jobs]   # default: all
```

- header: overall status, agent version, last update, pending agent update, refresh button;
- current issues with their message;
- system chips (CPU temperature, load, memory, uptime, pending reboot, power, clock,
  updates, services, kernel log);
- disks (model, size, power-on hours, last self-test, temperature);
- filesystems with usage bar and thresholds (read-only flagged);
- RAID arrays and ZFS pools (state, capacity, last scrub);
- graphics cards (temperature, power, fan, load and video memory bars);
- dirvish vaults with last success, size and file count, and a per-day timeline (success / warning / failure /
  running);
- jobs with last success.

Every row opens the corresponding entity. Colours follow the theme (`--success-color`,
`--warning-color`, `--error-color`). Development: `cd card && npm ci && npm run build`
writes `custom_components/host_agent/frontend/host-agent-card.js` (git-ignored, built by
the release workflow).

### Removal

Deleting the integration entry stops and removes the agent, its configuration and Home
Assistant's access (sudoers rule and key), and deletes the MQTT device. The two accounts are
left in place (`userdel host-agent host-agent-admin` to remove them).

## Development

```bash
pip install pre-commit && pre-commit install   # ruff, shellcheck, tsc, JSON/YAML checks...
scripts/bundle_agent.sh                        # embed the agent in the integration
(cd card && npm ci && npm run build)           # build the card served by the integration
pytest agent/tests tests/integration           # + sudo pytest tests/remote (helper, needs root)
```

CI: `pre-commit`, `Validate with hassfest`, `Validate with HACS`, `Agent`, `Integration`.

## Releasing

**Actions → Release → Run workflow**, enter the version (`0.2.1`, or `0.3.0b1` with
*pre-release* checked). The workflow:

1. runs the agent, integration and helper tests;
2. sets the version in `agent/src/host_agent/__init__.py` and `manifest.json`, commits,
   tags `vX.Y.Z` and pushes;
3. builds the agent archive with Python 3.11 and embeds it in the integration;
4. publishes the GitHub release with `host_agent.zip` (HACS), `host-agent.pyz` and its sha256
   (manual installs), with generated release notes.

The agent and the integration always share the same version: the integration installs
exactly the agent it ships. In a development checkout, `scripts/bundle_agent.sh` embeds a
locally built archive (git-ignored).

`Validate` runs the HACS and hassfest checks needed for the HACS default list (which also
requires the icon in [home-assistant/brands](https://github.com/home-assistant/brands)).

## Alert blueprint

[![Import blueprint](https://my.home-assistant.io/badges/blueprint_import.svg)](https://my.home-assistant.io/redirect/blueprint_import/?blueprint_url=https%3A%2F%2Fgithub.com%2FElwinmage%2Fha-host-agent%2Fblob%2Fmain%2Fblueprints%2Fautomation%2Fhost_agent%2Fhost_agent_alert.yaml)

`blueprints/automation/host_agent/host_agent_alert.yaml`

- no entity to choose: by default it watches the **Problem** sensor of every host, hosts
  added later included (one alert per host, listing all its issues); select problem
  sensors (hosts, disks, filesystems, vaults…) to restrict it;
- alert after a confirmation delay when a problem sensor turns on, filtered by severity;
- new alert when another issue appears while a problem is active;
- "back to normal" and "agent offline / back online" alerts (LWT based);
- optional persistent notification, kept up to date and dismissed when resolved;
- your own actions (mobile app, Telegram, e-mail…) with `title`, `message`,
  `severity`, `event`, `host`, `issues` variables;
- no alert storm when Home Assistant restarts.

The integration fires a `host_agent_problem` event for every change of a problem sensor,
usable in your own automations too:

| Field | Content |
|---|---|
| `transition` | `problem` (off → on), `new_issue` (issues changed while on), `resolved` (on → off), `offline` (→ unavailable), `online` (unavailable → known) |
| `entity_id`, `name` | problem sensor |
| `host`, `node_id` | host |
| `host_sensor` | `true` for the host's own Problem sensor, `false` for a disk, filesystem, vault… |
| `kind` | `host`, `disk`, `filesystem`, `vault`, `job`, `system`, `gpu`… |
| `state`, `previous_state`, `issues`, `previous_issues` | new and previous values |
| `elapsed` | seconds spent in the previous state (for `new_issue`: since the problem started) |
| `since` | start of the new state (ISO 8601) |

Example action:

```yaml
- action: notify.mobile_app_pixel
  data:
    title: "{{ title }}"
    message: "{{ message }}"
    data:
      priority: "{{ 'high' if severity == 'critical' else 'normal' }}"
```

See [agent/README.md](agent/README.md) for installation, entities and the MQTT contract.
